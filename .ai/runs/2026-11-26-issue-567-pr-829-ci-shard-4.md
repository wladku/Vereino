## Steps

1. Read the job log. The failing test was `foundation/ISSUE-629-retire-club-schedules.spec.ts` › many-clubs TEST-M06. It failed on the first try and on the retry, at line 140 with `TypeError: Cannot read properties of undefined (reading 'filter')`: the object that `mercato(['foundation', 'club-jobs', 'sweep'])` returned had no `sweeps` field. This PR does not touch that spec, the `club-jobs` CLI or the fixture.
2. Merged `origin/main` (cc3de13d). The owner had already pushed the same merge (694bfe00, identical tree), so the run continued from that commit.
3. Root cause. `mercato()` in `_fixtures/club.ts` returns the last stdout line that starts with `{`. Under the ephemeral runner, the platform logger (pino) writes JSON records to stdout. Its default destination is an asynchronous sonic-boom stream on fd 1, while the CLI writes its result with a synchronous `process.stdout.write`. So a record logged before the result (the sweep logs `Club job sweep finished` for each job type) can still reach stdout after it, and the parser then reads that log record. The existing lesson `cli-json-result-line-is-not-the-last-json-line` described the symptom for TEST-M07, but the shared helper was never fixed.
4. Fix. `mercato()` and `mercatoAsync()` now run the CLI with `OM_LOG_DESTINATION=stderr`, the platform logger's own switch (`@open-mercato/shared` `transport.server.js`). Stdout now carries only the command's output. A probe of the platform logger showed the record goes to stdout without the variable and to stderr with it. No assertion was weakened.
5. Updated the lesson with the cause and the fix.
