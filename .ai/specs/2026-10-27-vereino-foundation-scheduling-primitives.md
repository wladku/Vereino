## TLDR

Phase 2 is the product core: the coordinator builds a schedule from recurring rules, parents and participants declare according to the club's policy, coaches check off attendance, and every later phase reads the same calendar. The club management spec designs each feature; the first foundation slice designs the kernel. Between them sits a layer no document owned: how a recurrence rule becomes sessions and survives edits, how a status moves forward and never back, how a conflict check from a module that may not be enabled is consulted, how a read of personal data leaves a durable record, how a module's scheduled jobs are registered once, and how a calendar renders for a guardian on a phone and a coordinator at a desk. This specification designs those **scheduling, attendance and roster primitives** — seven built with E03 (`Recurrence` + `expandOccurrences`; `defineTransitions` + `advanceWhere`; pure overlap maths with the `vereino.occupancyProvider` contract; `registerModuleSchedule` with a worker convention; `CalendarItem` with a Tailwind `CalendarList` and a `toScheduleItem` adapter for the installed coordinator calendar; `auditedRead` over a module-owned append-only log; and that log's base class `AppendOnlyEntityBase`, whose first consumer turned out to be the contacts audit of #34) and one designed for later (`CsvExport`); the import pipeline stays deferred because V-14 removed its second consumer. No new npm dependency: the recurrence subset runs on the already installed `date-fns` 4.4 and `date-fns-tz` 3.2. The club spec's phase 2 is marked ready in the same PR: V-6 confirmed, V-8 partially (the family serves the coordinator view only), V-14 negative (fixtures stay a manual import), DD-11 superseded, DD-20 superseded in part.

## Problem Statement

Two modules (`groups`, `activities`), seven jobs across phases 2–5, four forward-only status machines and three calendars are planned on the same handful of mechanics. The club spec names them — RRULE expansion with a horizon, detached sessions, "status condition in the UPDATE", append-only entries, audited reads, the facility guard — but leaves their implementation to each story. Without this slice, #31 writes a recurrence expander, #33 a conditional-update helper, #34 an audit writer, phase 5 a second conflict check, and the architectural review's phase 2 findings stay open. The opposite risk is the one the first slice's reviews corrected: wrapping what the platform already does. The verifications show the platform provides the scheduler, notifications, dictionaries and a schedule UI family — and that its access log keeps non-core rows for eight hours by default (V-F08), which is why the contacts audit needs a module-owned log rather than a wrapper. This slice composes the platform and adds only the pure maths, the seams and two small components.

- **Market / product reference (verified 2026-10-27):** the installed `@open-mercato/ui/backend/schedule` family (`ScheduleView`, `ScheduleAgenda`, `ScheduleGrid`, `ScheduleToolbar`; `ScheduleItem` with a four-value status, semantic tokens, `linkLabel` rendered only by the grid, day buckets in the browser zone) — *adopted* for the coordinator's plain calendar through an adapter, *not* for the member agenda; the core `customers` `CalendarScreen` (bespoke, not exported) — *studied, not reused*; the installed `audit_logs` access log (`AccessLogService.log/logMany`, 8-hour retention for non-core resource kinds) — *used only as a mirror*, the durable record is the module's own append-only table; RFC 5545 via the `rrule` library (club spec DD-11) — *rejected* for the subset the club needs; iCal `UNTIL`, `COUNT` and `EXDATE` semantics — *adopted* in the subset so a future swap is a parser change; Odoo's "status condition in the UPDATE" for job-advanced states — *adopted* as `advanceWhere`, wrapped in a command so events and the lock token survive.

## Goals

- **REQ-G01** (Must) — A recurring activity is stored as a standard RRULE string of the supported subset, expanded into sessions in the club's time zone for a rolling horizon, with exceptions, detached sessions and re-generation that never touches a session with attendance or a substitution (club spec REQ-005, TEST-007).
- **REQ-G02** (Must) — Every forward-only status (session, declaration; later charge, campaign, rental) is declared once as a transition table with its entry states, asserted in commands and advanced by job-driven commands through a conditional UPDATE that reports the ids it won.
- **REQ-G03** (Must) — Session conflicts are computed by one pure overlap function over a place's capacity and a coach's time, with the place tree projected onto the candidate by `activities`; an optional occupancy provider (facilities, phase 5) adds bookings and closures without `activities` knowing the module.
- **REQ-G04** (Must) — Reads of personal data that the club spec marks as audited (guardian contacts, DD-39; later bank statements) leave one durable row in a module-owned append-only log with ids and a purpose — never values — before the data is returned, and are mirrored to the platform's access log.
- **REQ-G05** (Must) — A module registers its scheduled jobs idempotently from `seedDefaults` with a stable id through one helper and ships workers under the module-prefixed ids the platform requires, taking scope from the registration only and logging counts (S4.7; V-6).
- **REQ-G06** (Must) — Calendars share one `CalendarItem` type: the member calendar is a phone-first Tailwind list, the coordinator calendar is the installed `ScheduleView` behind a `toScheduleItem` adapter; conflicts and filters live outside the calendar components (V-8b).
- **REQ-G07** (Should) — `CsvExport` is designed here and built with its first in-scope consumer; the import pipeline stays deferred; nothing held back by A05 is built (Q5, Q7, Q8).
- **REQ-G08** (Must) — The club spec's phase 2 is marked `Ready for implementation` in the same PR, with V-6, V-8 and V-14 recorded, DD-11 superseded, DD-20 superseded in part (in the facilities spec `2026-10-27-vereino-facilities.md`, where D-028 moved it) and REQ-039 re-scoped to a manual import.

## Non-goals

- Re-documenting or wrapping the platform: the `scheduler` module's registration and workers beyond one upsert helper, `notifications` (`notifications.ts` + `notificationService`), `dictionaries` (seeded with `em`), the schedule UI family, `authorizeScoped` and the first slice's primitives.
- The features of E03 — groups, memberships, the activity wizard, the attendance list, the contacts endpoint — stay in the club spec and in `groups`/`activities`; this spec delivers primitives and their tests, and names the story whose PR wires each one.
- Substitutions, the "needing a coach" list, the units report and coach settlement (held back, A05): nothing is built; `CsvExport` is designed only.
- Live integration with PZPN / "Łączy nas piłka": V-14 is negative (HTML only, a captcha-gated internal API, terms of use that forbid database extraction); REQ-039 becomes a manual CSV/paste import inside `activities`, later.
- Resource lanes, drag-and-drop or per-group colours in calendars: the installed family has none (`ScheduleItem.color` is never read); a wrapped `react-big-calendar` is out of scope for 1.0.
- A new club setting for the horizon: DD-10's constant of 16 weeks stays.
- Push notifications, messenger integration (N02, N03).

## Proposed Solution

Pure maths and types in `@vereino/core` (`Recurrence`, `Interval` overlaps, transition tables, `CalendarItem`), ORM- and DI-bound helpers in `src/modules/foundation/services/` (`advanceWhere`, `auditedRead`, `registerModuleSchedule`, the `vereino.occupancyProvider` token; S4.2 keeps `lib/` free of the ORM and the container), the append-only base in `@vereino/db`, two components in `@vereino/ui` (`CalendarList`, `toScheduleItem`), and the rest in the consuming modules: `activities` owns the generator, the policy resolver, the conflict call site, its jobs and its notification types; `groups` owns memberships and the age-category seed. `@vereino/core` declares `date-fns` and `date-fns-tz` as exact-pinned dependencies (V-F06). Every helper composes an installed seam the verifications located; the one place the platform's seam does not fit — the access log's eight-hour retention — is bridged by a module-owned table, not by a wrapper.

| **DD-G01** Recurrence is an own value type in `@vereino/core` covering the RRULE subset `FREQ=WEEKLY`, `INTERVAL`, `BYDAY`, `UNTIL` / `COUNT`, plus `EXDATE`, serialised as a standard RRULE string; expansion uses `date-fns` + `date-fns-tz` in the club's IANA zone (Q2 = A). ## Domain Vocabulary and Business Rules

| Term | Definition | Owner | Rule / failure |
|---|---|---|---|
| Recurrence | `{ freq: 'WEEKLY'; interval; byDay: Weekday[]; until?: LocalDate; count?; exdates: LocalDate[] }`, parsed from and serialised to an RRULE string plus an `EXDATE` line; `starts_on`, `default_start_time`, `default_end_time` and the club `timezone` complete it (DD-G01) | `@vereino/core` | an unsupported RRULE part (`FREQ=DAILY/MONTHLY`, `BYMONTHDAY`, `BYSETPOS`, …) → `recurrence_unsupported` naming the part; `until` before `starts_on` or an empty `byDay` → `recurrence_invalid` (both 422, thrown by `foundation`'s parse service) |
| Horizon | The window `[today, today + 16 weeks]` (DD-10, not beyond `ends_on`) the generator fills; `generated_until` records the last generated date | `activities` | the daily job extends the horizon; an edit regenerates within it |
| Occurrence (session) | One generated or manually created row with `start_at`/`end_at` instants, `occurrence_date` (club-zone date), `status`, `is_detached` | `activities` | unique (`activity_id`, `occurrence_date`) for non-detached rows (DD-G03) |
| Transition table | `{ states, entry: State[], transitions: Array<[from, to]>, terminal: State[] }`; `canTransition(from, to)`; `terminal` states have no outgoing edge | `@vereino/core` | an illegal transition in a command → 409 `invalid_transition` naming both states; a job-driven command that loses the race counts `skipped` |
| Interval | `{ start: Date; end: Date; resourceId; id }`; overlap = `a.start < b.end && b.start < a.end`; a resource conflicts when the overlapping intervals exceed `capacityOf(resourceId)` | `@vereino/core` | half-open: a session ending at 18:00 does not conflict with one starting at 18:00 |
| Occupancy provider | An optional DI service (`vereino.occupancyProvider`) that returns blocking intervals for a set of place ids and a window (bookings, closures, maintenance); the contract is defined here, its implementation is phase 5 | `foundation` contract; `facilities` implementation | absent → no extra intervals; throws → the save fails closed (uncoded 500, DD-G14), the preview shows "could not check bookings" |
| Audited read | A read whose row in the module's append-only access log is committed before the data leaves the server (DD-G06) | `foundation` service; the module's log table | the log write failing → the read is not performed |
| Append-only entity | A row with `id`, `tenant_id`, `organization_id`, `created_at` and no `updated_at` / `deleted_at`; updates and deletes are refused by a `foundation` ORM guard | `@vereino/db` base; `foundation` guard | update or delete → 409 `append_only` |
| Module schedule | One `ScheduledJob` row per organization for a job `${module}:${name}` (DD-G07) | `foundation` helper; the module's `setup.ts` and `workers/` | a run returns `{ processed, failed, skipped }`; a throw is retried by the queue; `concurrency: 1` plus the conditional UPDATEs prevent double work |
| Calendar item | `{ id, kind: 'training' \| 'match' \| 'class' \| 'event' \| …, title, startsAt, endsAt, status: 'planned' \| 'done' \| 'cancelled', placeName, groupName, personIds[], href, actions: Array<{ id, label, href }> }` — the one shape every calendar consumes | `@vereino/core` | `startsAt < endsAt`; `status` from the session transition table |

## Users, Permissions, and Scope

The slice adds no actor and no ACL feature; every helper runs inside the consuming module's command or route (`activities.manage`, `activities.coach`, `activities.attendance.declare`, `activities.view`, `people.self` — the club spec's table) through `authorizeScoped` (foundation P-02) with the allowed grant kinds the story names: coordinator (`section_ids`) for activities, coach (`coached_group_ids`) for attendance and contacts, guardian / self for declarations (also from a token through P-10). Reopening a `cancelled` or `done` session (the club spec's *Session* row) is a `reopen` transition with a required reason, allowed only for the `club_admin` grant. The occupancy provider runs in the caller's scope. `auditedRead` records the acting role `authorizeScoped` derived.

## Architecture and Data Flow

```text
@vereino/core: Recurrence ─► expandOccurrences(rule, anchor, window) ─► local wall time → fromZonedTime → instants
activities command activities.activities.create/update (execute → authorizeScoped):
   parse RRULE (foundation parse service → 422 recurrence_unsupported / recurrence_invalid)
   ─► preview = expandOccurrences(horizon) ─► candidates as Intervals keyed by the place id and by the coach id
   ─► existing planned sessions on the place's ancestors/descendants re-keyed to the candidate place id; the coach's sessions keyed by coach id
   ─► occupancyProvider? (hasRegistration) → extra blocking intervals (facilities, phase 5)
   ─► findOverlaps(candidates, existing, capacityOf) [core] ─► 409 occurrence_place_conflict with the list
   ─► write activity + sessions (runCrudCommandWrite); generated_until; events activities.activity.created / occurrence.generated (batched)
```

## Data Models

This slice owns no table. It defines:

- `AppendOnlyEntityBase` (`@vereino/db`): `id`, `tenant_id`, `organization_id`, `created_at` — no `updated_at`, no `deleted_at`; subclasses add their columns; the `foundation` guard (a MikroORM event subscriber for entities marked `appendOnly`) throws 409 `append_only` on update or delete.
- `ContactAccessLog` / `activities_contact_access_log` (owned by `activities`, the first P-28 consumer; the club spec's data model gains this row in the readiness amendment): `AppendOnlyEntityBase`; `actor_user_id` uuid; `acting_role` text; `occurrence_id` uuid; `resource_kind` text (`people:person`); `resource_ids` uuid[]; `purpose` text (`coach_contacts`); index (`organization_id`, `occurrence_id`, `created_at`); no sensitive column — ids only.
- The stored recurrence format on `activities_activities.recurrence_rule` (club spec column): an RRULE string of the DD-G01 subset, exceptions as an `EXDATE:yyyymmdd,…` line; `generated_until` as the club spec defines it; the horizon is DD-10's constant.
- Transition tables (data, not schema): sessions — states `planned`, `done`, `cancelled`; entry `planned`; transitions `planned → done`, `planned → cancelled`, `cancelled → planned` (`reopen`), `done → planned` (`reopen`); terminal: none (the club spec's *Session* row allows the administrator to reopen with a reason). Declarations — states `pending_guardian`, `final`, `rejected_by_guardian`; entry `final` (policy `immediate`) and `pending_guardian` (policy `guardian_confirm`); transitions `pending_guardian → final`, `pending_guardian → rejected_by_guardian`; terminal `final`, `rejected_by_guardian`; the `declared` value may change until `start_at` without a status change.
- `CalendarItem` (type only, core).

## Security, Privacy, and Compliance

- **Authorization and scope:** every helper runs inside a command that calls `authorizeScoped` (job-driven commands with the `system_job` source) or a route that filters with `scopeWhere` / checks with `assertInScope`; the calendar endpoint returns only the grants' sessions (`as` is a view filter, the scope decides); the occupancy provider is called in the caller's scope and returns ids and times only; `reopen` needs the `club_admin` grant and a reason.
- **Audited reads:** DD-G06 — the module's append-only row is committed before the data is read; `resource_ids` only; `purpose` from a fixed enum (`coach_contacts`, later `statement_view`); the consent filter (`share_contact_with_coaches_at`) is applied before `auditedRead`, so withdrawn consents are never read; the platform access log is a mirror whose retention is the operator's (`AUDIT_LOGS_NON_CORE_RETENTION_HOURS`), never the evidence.
- **Tenant isolation:** jobs take scope from the sanitised payload the platform injects (V-6); the worker re-validates it; `advanceWhere` always includes `tenant_id` and `organization_id` in its `where`.
- **Time:** every instant is computed through `fromZonedTime` with the club zone; cron schedules use the same zone and are re-registered when it changes; DST shifts are test cases (TEST-G01); `now` is a parameter everywhere in core (S3.5); `CalendarList` buckets days in the club zone, not the browser's.
- **Failure modes (S3.6):** unsupported RRULE → 422 before anything is written; provider failure → uncoded 500 on save with a fingerprint, a visible warning in the preview; the log write failing → no data; a job-driven command losing a race → `skipped`; a registration failing → logged by the platform and retried at the next `seedDefaults`; `CalendarList` receiving an invalid item → dropped with a fingerprint.
- **Compliance:** no new personal data; the contacts log holds ids; the PZPN decision (V-14) keeps the club clear of the portal's terms of use — the coordinator enters fixtures by hand or from a file she downloads herself.

## Risks and Tradeoffs

| Risk / tradeoff | Impact | Mitigation / detection | Residual risk |
|---|---|---|---|
| The RRULE subset is outgrown (monthly rules, "last Friday") | a rule the club cannot enter | the string stays standard; widening the parser is additive; `recurrence_unsupported` names the part so the gap is visible | a later `rrule` swap costs a parser change, not a migration |
| DST and zone bugs in own date maths | sessions an hour off twice a year | TEST-G01's explicit DST cases including the 02:30 gap; `fromZonedTime` only, never manual offsets | none beyond test coverage |
| `ScheduleView` at narrow widths | a coordinator on a phone scrolls horizontally | the phone path is `/club`; the desk view accepts `overflow-x-auto` (V-8b) | accepted |
| The family changes in a platform upgrade (four-value status, no `color`) | the adapter breaks | `toScheduleItem` is one function with a unit test; upgrade runs re-run TEST-G07 | an upgrade run revisits P-23 |
| The occupancy contract has no implementer before phase 5 | an unused token | the contract is a name and a `hasRegistration` branch; TEST-G04 proves both branches with a fake | none |
| The platform access log mirror rotates after 8 hours | an operator expects the mirror to be the evidence | DD-G06 names the module log as the record; the deployment runbook sets `AUDIT_LOGS_NON_CORE_RETENTION_HOURS` for the mirror | none for compliance |

| `advanceWhere` inside a command adds a select before the update | one more query per job run | the select is the id list the events need anyway | none |
