# `foundation` — shared Vereino primitives

Helpers that compose the installed Open Mercato contracts (commands, DI, `auth`, encryption, scheduler, i18n) so every Vereino module implements each mechanic once. Specification: [`.ai/specs/2026-10-27-vereino-foundation-primitives.md`](../../../../../.ai/specs/2026-10-27-vereino-foundation-primitives.md) (P-01…P-19), for module jobs [`.ai/specs/2026-10-27-vereino-foundation-scheduling-primitives.md`](../../../../../.ai/specs/2026-10-27-vereino-foundation-scheduling-primitives.md) (DD-G07) and, for messages, [`.ai/specs/2026-10-27-vereino-foundation-messaging-primitives.md`](../../../../../.ai/specs/2026-10-27-vereino-foundation-messaging-primitives.md) (P-29…P-31, phase A, #71). The module owns the dispatch outbox (`foundation_dispatches`, `foundation_deliveries`), the event `foundation.dispatch.delivery_failed` and the jobs `foundation:dispatch-deliver` and `foundation:dispatch-sweep`; it owns no route, page or ACL feature.

## What a primitive is

A **primitive** is a mechanic built once as a shared unit with its own tests (an id `P-nn` in the spec's _Reuse and Ownership Map_); a **helper** is a small shared function without an inventory claim; a **convention** is a platform mechanism used one fixed way. Nothing here re-wraps a platform API that is already one call — modules keep the platform's `CommandHandler`, `makeCrudRoute`, subscriber `metadata`, worker files and injection widgets.

**Inventory rule (REQ-F16).** A primitive may be built before its second consumer only when it is listed in the spec's inventory with at least two backlog stories and ships a self-contained test. Anything else stays in its module until a second module needs it.

**Where code goes.** Framework-free types, predicates and policies → `@vereino/core`; the entity base and column options → `@vereino/db`; code that binds the ORM, DI or the platform → `services/` here (covered by integration tests, S13.1); pure code of this module → `lib/` (100 % unit coverage).

## Conventions

- **Commands.** `execute` calls `authorizeScoped(spec, input, ctx, em)` first, inside the write transaction; the result's `actingRole` goes into the command result and `buildLog` writes it to `context.actingRole`; `authorizeReplay` calls it again with `{ mode: 'replay' }` and the handler sets `atomicReplay: true`.
- **Denials (#76).** A session scope that holds no grant beyond `self_user` means the account is not linked to a person of this club (`lib/scope-denial.ts`): `authorizeScoped` refuses it with 403 `scope_unlinked` before `loadTarget` (unless the command accepts `self_user`), and `assertInScope` answers `scope_unlinked` instead of `scope_denied` for it. A linked user outside the target's grants, a marker scope and a job scope keep `scope_denied`. Pages that render their own 403 state show `foundation.errors.scope_unlinked` when the code is `scope_unlinked`; `CrudForm` pages show the server's message.
- **Lists.** `list.buildFilters` returns `{ $and: [scopeWhere(await scopeContract.resolve(ctx), allowedKinds, columnMap), businessFilters] }` and the route sets `export: { enabled: false }` (the platform's full export skips `buildFilters`); without a matching grant `scopeWhere` yields `{ id: { $exists: false } }` (`id IS NULL`), because the query engine turns an empty `$in` into invalid SQL. Detail routes load the row in the trusted organization and call `assertInScope`. No hand-written scope check elsewhere.
- **Role sync.** `syncAuthRoles(userId, desired, ctx)` accepts the role list or a function of the current roles (`(current) => desiredRoles({ currentRoles: current, … }, today)`), evaluated under the per-user lock.
- **Subscribers.** A persistent subscriber is the platform shape `metadata { event, persistent: true, id: '<module>:<kebab-name>' }` + `handle`; it is idempotent through the consumer's unique constraint or a set comparison, and a failure is retried by the queue.
- **Jobs.** A module job is registered from `setup.ts` `seedDefaults` with `registerModuleSchedule(container, { module, name, schedule, scope })` — one schedule per organization, never thrown from setup; it takes its scope from the registration, is idempotent and logs `{ processed, failed, skipped }` (S4.7).
- **Worker files (DD-G07).** `workers/<name>.ts` exports `metadata = { queue: '<module>-<name>', id: '<module>:<name>', concurrency: 1 }` and a default `handle(job, ctx)` that re-validates the injected `tenantId` / `organizationId` with Zod and dispatches one module command with `jobCommandContext(container, scope)` (scope source `{ job: true }`, acting role `system`).

## Messages (foundation III phase A, #71)

- **Audience (P-29).** A consumer passes an `AudienceSpec` (`{ kind, ids? }`) and its trusted context (`{ container, tenantId, organizationId, scope, em? }`, `scope` from `scopeContract.resolve` or a job's `system_job` grant) to `resolveAudience`. The provider of the kind returns members active on the club's date; the contact resolver adds the active guardians of minors, accounts, addresses (decrypted in memory only), languages (person → club default) and the club's name and date; `expandAudience` applies the _Thread_ rule — a minor with an account is kept beside their guardians, a minor without one is reached through them, account holders get in-app and e-mail, people with an address e-mail only, the rest are unreachable. A `persons` id outside the author's scope refuses the whole request (403 `scope_denied`); `exclude` drops the author. A kind no module registered answers 422 `audience_kind_unavailable`; a missing contact resolver is an uncoded 500 with the fingerprint `foundation.audience.contacts_unavailable`. `resolveMembers(members, ctx, { exclude })` applies the same contacts, guardians, expansion and 2000 cap to members a caller has already chosen and authorized, without a provider (a member's direct thread, foundation III DD-M18); `resolveAudience` runs the same expansion after its provider and the `persons` check.
- **Dispatch (P-30).** In the command transaction: `dispatch.enqueue(em, { template, params, recipients | audience, exclude?, source, idempotencyKey, secrets?, actor }, ctx)` returns `{ dispatchId, created }` — one dispatch per key and organization, one delivery per recipient and channel (an unreachable person gets one `skipped` / `unreachable` row), secrets (a raw link token per person id) only on the e-mail row, encrypted. Unknown template → 500 `foundation.dispatch.unknown_template`; a `preferences` template → 500 `foundation.dispatch.optout_unavailable` (Q15 = B); params failing the template's schema → 422 `dispatch_params_invalid`. After commit: `dispatch.publish(dispatchId, scope)` enqueues `{ deliveryId | dispatchId, tenantId, organizationId }` jobs on `foundation-dispatch` (a failure is left to the sweeper). For staff views, `dispatch.deliveriesOf(dispatchId, page, ctx)` pages one dispatch's deliveries and `dispatch.countsOf(dispatchIds, ctx)` counts the deliveries of several dispatches by status (the thread page, #103) — never an address.
- **Delivery.** `foundation:dispatch-deliver` (concurrency 5) reads the row by id, tenant and organization (a forged job is refused and logged as `foundation.dispatch.job_scope_mismatch`), leases it with the attempt counted, renders and sends at most 8 e-mails per second per process through `foundation.emailSender`, and writes the final state: `sent`; `failed` with `transport_unavailable` (after the 5th transient attempt, backoff 1, 5, 15, 60 min), `provider_rejected` or `address_invalid` (at once; the platform's `classifyOutboundError` decides), `render_failed`; `skipped` / `delivery_disabled` under `OM_DISABLE_EMAIL_DELIVERY`. The final state wipes the address (the hash stays) and the secret; each failure emits `foundation.dispatch.delivery_failed` `{ id, dispatchId, tenantId, organizationId }`. In-app: one `createBatch` per dispatch, `channels: ['in_app']`, `groupKey` = the dispatch id, the type's keys only. Delivery is at least once: a crash after the send resends once when the lease expires. `foundation:dispatch-sweep` (every 2 minutes per organization, registered by `setup.ts`) republishes due work and fails deliveries out of attempts.
- **Templates (P-31).** `defineEmailTemplate({ id, notificationType, optOut, params, subject, body, text, preheader?, link?, actionLabel? })` and `registerEmailTemplate(container, template)` in the sending module's `di.ts`. The worker renders with the recipient's dictionary inside `EmailLayout` (club name, preheader, body, button, footer with the reason in the recipient's language); club text goes through `clubText` (escaped, line breaks kept). The in-app type a template names must be declared `channels: ['in_app']`, so the platform's notification e-mail never sends a Vereino message.
- **Tests.** The integration tests (TEST-M01…M04, `.ai/qa/tests/foundation/messaging/`) drive these services through the QA probe `.ai/qa/tests/_fixtures/messaging-probe/probe.mjs`, which adds probe templates, a probe in-app type and a scripted sender in its own process; the shipped modules contain no probe.
