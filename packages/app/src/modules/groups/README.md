## Scope

Groups and rosters are read with the grant kinds `coach` (the group ids of the caller's active `coach`/`assistant` memberships), `coordinator` (the group's section) and `club_admin`, least-privileged first, so the detail route's `actingRole` is `coach` for a coach of the group. The roster list narrows to the groups `scopeWhere` admits on the groups table (memberships carry no section). Groups and memberships are written by a coordinator within their sections and by the club administrator; moving a group to another section needs both sections in scope. Seasons and external teams are club-wide dictionaries: read by every coach, coordinator and the club administrator, written by every coordinator and the club administrator (`clubWideKinds: ['coordinator']`).

## Coach scope and roles

`people.scopeService` stays the single scope provider (foundation DD-F03). `people` declares the contract of an optional contribution (`people/services/membership-contribution.ts`) and resolves it with `hasRegistration`, the pattern the club spec names for `facilities.maintainerScopeProvider`; `groups` registers it, so the dependency stays `groups` → `people`. Without `groups` there is no coach grant and no participant payer. A `coach` role assignment grants only the `vereino_coach` `auth` role (the `groups.view` feature); the coach's groups come from memberships — both are needed before a coach sees a group (#26).

## Rules

- Team fields (`age_category_entry_id`, `league`, `season_id`) on a `class_group` → 422; the form clears them when the kind is a class group.
- A membership write takes the group's row lock first, then refuses an overlapping live membership of the same person, group and role (409 `membership_overlap`); the partial unique index on open-ended rows backs it.
- A membership is ended through `valid_to` (`POST …/end`, default today in the club zone) and stays in the roster; there is no delete.
- A group with any live membership (ended ones included) is not deleted (409 `group_has_memberships`); deactivate it.
- A season named by a live group is not deleted (409 `season_in_use`); group writes that name a season row-lock it.

## Deferred

The public fields (`is_public`, `public_description`, `public_conditions`, `age_from`/`age_to`, `level_label`, story #29); sessions and attendance (`activities`, #31 and later), the 409 on changing `kind` to `class_group` when the group has matches, and `match`/`sparring` for a class group → 422 (with activities); the person record's "Groups" tab; `search.ts` (no `groups` entity is listed for search).

## Age categories (#92)

A team's PZPN age category is an entry of the club's dictionary `groups.age_categories` in the platform `dictionaries` module (club spec REQ-019, E06-S10). `setup.ts` `seedDefaults` creates it once per club with the eight PZPN categories (Skrzat … Senior, a system dictionary sorted `created_at_asc`); `yarn mercato groups seed-age-categories --tenant <id> --org <id>` (`cli.ts`) does the same for a club set up before #92 and prints `{ "created": true|false }` — a club that has the dictionary keeps it as its administrator left it. The club administrator edits the entries on `/backend/config/dictionaries`; every reader of groups gets them from `GET /api/groups/options/age-categories` (`services/age-categories.ts`), so coordinators and coaches need no `dictionaries` feature. A write checks that the id is an entry of the club's active dictionary (422 `groups_reference_invalid`, `field: ageCategoryEntryId`). The platform hard-deletes entries: a group whose entry was removed keeps the id and shows no category.

Each category carries a PZPN "U" range in `groups_age_category_ranges` (people life-cycle spec REQ-L16, DD-L17, #384), keyed by the entry id so a renamed category keeps it; `seedDefaults` and the CLI seed it with the defaults of `PZPN_AGE_CATEGORIES`, migration E gave existing clubs the same ranges for entries that still carry the default values. In reference year R (the year the season starts, else the year of today) "U{from}–U{to}" means the birth years `R − u_to + 1` … `R − u_from + 1` (`birthYearsOf`, `fitsAgeCategory` in `lib/groups-rules.ts`). The tab **Age categories** (`/backend/groups/age-categories`, after Seasons) lists them for a chosen season; the club administrator edits a range in its row and adds a category with its range in one dialog. A team's public tab proposes "Age from" = u_from − 1 and "Age to" = u_to while both are empty and shows "Rocznik {years} w sezonie {season}"; the team form shows the birth years under the category.

## Section usage (#85)

`groups` registers `groups.sectionUsage` for the `club_core` deactivation guard and the response enricher `groups.section-groups` on `club_core:section` (`data/enrichers.ts`), which adds `_groups: { activeGroupCount }` to every row of `/api/club_core/sections`. A group create, an activation and a move read the target section through `clubCoreDirectory.lockSectionForShare` (`FOR SHARE`), so they serialize with a section deactivation, which holds the row `FOR UPDATE` (UX parity spec DD-U08).

## Public catalogue (#91)

A group carries public fields (club spec `groups_groups`, DD-29): `is_public` (default false), `public_description`, `public_conditions`, `age_from` and `age_to` (0–99 years; from above to → 422 `group_age_range_inverted` on `ageTo`, checked on the merged values of an update) and `level_label`, edited on the B-12 "Public page" tab by whoever edits the group (`groups.manage` in scope). `groups.publicCatalog` (`services/public-catalog.ts`, pure rules in `lib/public-catalog.ts`) is the optional block provider `club_core` reads with `hasRegistration` for a club that publishes `description_schedule` (key `groups`): a card per live, active, public group of the public section, with requirements only when the club publishes `conditions` and instructors only with `coaches`. An instructor is a person with an active `coach` or `assistant` membership; the card names them "First L." only when `people.personDirectory.publicNames` returns a name (the person's `publish_name_consent_at`), otherwise the name is null and the page says "Section coach" or "Section instructor". `groups.directory.publicGroups(scope, sectionIds)` names the public groups for the `activities` schedule block. On the club page the same provider sends `{ counts: { [sectionSlug]: n } }` — the number of live, active, public groups of each public section — for the tile text "{n} groups — see classes" (#89).

## Groups list and record as in the mockup; the match guard (#266)

Groups and activities parity spec phase 1 ([`.ai/specs/implemented/2026-11-14-vereino-parity-groups-and-activities.md`](../../../../../.ai/specs/implemented/2026-11-14-vereino-parity-groups-and-activities.md), REQ-A01, REQ-A02, TEST-A01, TEST-A02; README B-11, B-12).

- **List (B-11).** The subtitle, the kind as a badge, "Category / level" (a team's age category, else the level — `categoryOrLevel` in `lib/group-list.ts`), "Public" as a badge and the filter `isPublic` (`GET /api/groups/groups?isPublic=true|false`, kept in the URL like every other filter). The row action "Activities" (for `activities.view`) opens `/backend/activities/activities?groupId=<id>`.
- **Record (B-12).** The tabs Details / Roster / Public page in the mockup's order under `?tab=`, default `roster`; "Level" (`levelLabel`) on Details for both kinds; the header links "Activities" (for `activities.view`) and "Public preview" (the public page of the group's section, shown for a public group of a public section when the caller reads the club's and the section's slugs); "Edit age categories" beside the category select for `dictionaries.manage`.
- **Match guard.** `groups.groups.update` (and the undo of a "class group → team" change) refuses `team → class_group` while the group has live activities of type `match` or `sparring`: 409 `group_has_matches` with `details.total` and a field error on `kind`. The count comes from the optional DI contract `activities.groupUsage` (`matchActivityCount(em, { tenantId, organizationId, groupId })`), declared in `services/group-usage.ts` and registered by `activities`; without the registration the guard is skipped (no activity can reference the group), and a failing contract answers 503 `group_usage_failed`.

## The roster on the phone (#274)

Groups and activities parity spec phase 9 (REQ-A11, J-A01 step 4, D-031 §3). `/club/groups` lists the active groups the caller reads — the groups of a coordinator's sections, the groups a coach coaches; the record scope of `GET /api/groups/groups` decides, the page only names it — as cards with the section, the coaches and the active participants. `/club/groups/[id]` shows the roster as cards (name, role, age, dates in the reader's locale; the roster API carries no e-mail, phone or PESEL) in the views Active / Upcoming / History with their totals and "Show more" through every page (`sortField=roster`). With `groups.manage` the coordinator adds a person, edits, ends on a chosen last day and removes a mistake in bottom sheets: `MembershipDialog` and `EndMembershipDialog` take `surface="sheet"`, and the remove flow (`useRemoveMembership`, End offered on a used active row) is shared with the panel roster. A coach reads the roster without actions; another section's group answers "not yours" (403); both pages need `people.self` and `groups.view`, so a guardian gets the platform's access-denied page. The frame is `components/club/GroupsClubFrame.tsx` (the shared `MemberShell`, the profile over HTTP, the catalog prefix `groups.club.nav`), and the More entry "Groups" of `@vereino/ui` `member-nav.ts` is shown. ## Moving several children (#383)

People life-cycle spec phase L11 (REQ-L15, DD-L16, J-L09). `POST /api/groups/memberships/move-many` runs `groups.memberships.move_many` (`commands/memberships.ts`): with `dryRun` it previews, for 1–100 participant memberships of one group, per child `move`, `skip_already_member` or `skip_not_active` (the single move's rule, `planMove`), the declarations for the old group's sessions from the move day on, the fee note and the age fit (`fitsAgeRange`), with a 15-minute preview token (`lib/rollover-token.ts`); the apply moves every movable child or none in one transaction, drops those declarations there through `activities.groupUsage` (`pendingDeclarations`, `dropDeclarations`) and records them in the log, so one undo restores both groups and the declarations (`restoreDeclarations`). `{ undoToken }` on the same route undoes the caller's own move: a coordinator holds `groups.manage` but not the platform's `audit_logs.undo_self`. The roster's Active view selects rows for the bulk action "Move to another group"; `MoveChildrenDialog` (a dialog on the panel, a full-screen sheet on `/club/groups/[id]`) lists the active participants, ticks the selection, offers the chip **Fits {group}** once the target has an age range, and **Move {n}** previews the ticked children again and applies with that token (409 `move_preview_stale` refreshes the preview with a notice). `MoveChildrenNotice` shows the result with Undo. TEST-L21, TEST-L22.
